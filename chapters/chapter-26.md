**Глава 26. Аудит и оптимизация**

### Главная идея главы

Когда приложение собрано, начинается этап зрелости: не добавлять новое ради нового, а проверять качество уже существующего.  
Аудит FocusBoard 2026 проводим по четырём осям:

1. **Семантика**  
2. **Доступность (A11y)**  
3. **Производительность**  
4. **Архитектурная целостность**

Цель главы — зафиксировать критерии качества и привести проект к состоянию, в котором его можно уверенно развивать дальше.

### Что именно проверяем

| Область | Вопросы аудита |
|--------|-----------------|
| Семантика | Есть ли landmarks? Правильно ли используются `article`, `section`, заголовки? |
| A11y | Работает ли клавиатура? Есть ли доступные имена? Объявляются ли ошибки форм? |
| Performance | Не блокирует ли JS первую отрисовку? Есть ли приоритеты ресурсов и lazy-media? |
| Архитектура | Соблюдены ли границы компонентов, tokens, progressive enhancement? |

### Практическая задача главы

1. Провести чек-лист аудита FocusBoard.  
2. Зафиксировать результаты в документации.  
3. Внести точечные улучшения по итогам проверки.  
4. Отметить известные ограничения и следующий backlog.  
5. Подготовить проект к финальной главе с шаблонами и чек-листами.

- [x] Компоненты имеют одну ответственность
- [x] Есть design tokens
- [x] Есть docs по SSR и Progressive Enhancement

- Фильтрация задач пока логируется, но не полностью меняет DOM-список

#### Остальные файлы проекта

На этом этапе **не делаем больших рефакторингов ради рефакторинга**.  
Рабочие файлы (`index.html`, `styles/*`, `scripts/main.js`, `components/*`) остаются в финальной сборке Главы 25, потому что аудит подтвердил:

- архитектура уже согласована;
- базовые практики современного HTML соблюдены;
- улучшения дальше должны идти точечно, по backlog, а не через переписывание всего приложения.

Точечные optimization notes, которые уже учтены в текущей сборке:

- критический CSS раньше JS;
- `defer` / module scripts;
- lazy images + размеры;
- semantic landmarks;
- accessible form errors;
- progressive enhancement fallbacks.

### Практический мини-аудит (как выполнять)

#### 1. Семантика
- Есть ли один `main`?
- Видны ли landmarks в Accessibility Tree?
- Не используются ли «нейтральные» контейнеры там, где нужен смысл?

#### 2. A11y
- Tab / Shift+Tab по всему интерфейсу  
- Enter/Space на кнопках и summary  
- Escape для dialog/popover  
- Проверка сообщений ошибок скринридером  

#### 3. Performance
- CSS в критическом пути  
- JS не блокирует first paint  
- Картинки не вызывают CLS  
- Ниже-fold ресурсы не спорят с LCP  

#### 4. Архитектура
- Можно ли переиспользовать `task-card` на другом экране?  
- Понятен ли API компонента без чтения его shadow-DOM?  
- Остаётся ли страница полезной без JS?
