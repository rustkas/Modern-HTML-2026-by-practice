**Глава 23. HTML в эпоху SSR**

### Главная идея главы

После долгого периода доминирования клиентских SPA маятник архитектуры снова качнулся в сторону **Server-Side Rendering** и гибридных моделей. Причины простые:

- быстрый First Paint / LCP;
- лучшее SEO;
- устойчивость к медленному JavaScript;
- возможность отдавать полезный HTML ещё до гидратации.

В этой модели HTML снова становится центром архитектуры. Не «побочным продуктом фреймворка», а основным контрактом между сервером, браузером, поисковыми системами и UI-компонентами.

### Почему FocusBoard уже готов к SSR-мышлению

За предыдущие главы мы случайно (и намеренно) собрали SSR-friendly фундамент:

1. **Семантический HTML** — смысл доступен без JS  
2. **Declarative / Shadow DOM components** — разметка может прийти с сервера  
3. **Progressive Enhancement** — базовая функциональность не зависит от гидратации  
4. **Design tokens** — стили можно применять сразу к серверному HTML  
5. **Минимум клиентской логики в UI-примитивах** — компоненты не требуют сложного bootstrap

### Что особенно важно для SSR в современном HTML

| Практика | Зачем нужна |
|----------|-------------|
| Полноценный HTML с сервера | Быстрый FCP/LCP и доступность |
| Landmarks и семантика | SEO, a11y, AI-агенты |
| Declarative Shadow DOM | Инкапсуляция компонентов без клиентского рендера |
| Некритичный JS с `defer` | Не блокировать первую отрисовку |
| Токены и критический CSS | Стабильный первый экран |
| Работающие формы/диалоги на нативных возможностях | Меньше зависимости от гидратации |

### Практическая задача главы

1. Зафиксировать SSR-принципы проекта.  
2. Проверить, что ключевые части FocusBoard полезны без JavaScript.  
3. Подготовить HTML-контракт страницы как «серверный результат».  
4. Отделить то, что должно работать до JS, от того, что является progressive enhancement.  
5. Описать гибридную модель: server HTML → partial enhancement.

#### `docs/ssr-architecture.md`

```markdown
# SSR-архитектура FocusBoard

## Идея

FocusBoard проектируется так, будто HTML уже пришёл с сервера в готовом виде.

JavaScript не создаёт интерфейс с нуля, а **улучшает** уже существующий документ.

## Слои

1. **Server HTML**
   - семантика
   - landmarks
   - карточки задач
   - формы
   - начальное состояние UI

2. **Critical CSS / tokens**
   - первый экран стилизуется сразу
   - без ожидания JS

3. **Progressive Enhancement**
   - Navigation API / fallback
   - View Transitions
   - dialog/popover behavior
   - создание задач через templates

4. **Web Components**
   - усиливают инкапсуляцию и переиспользование
   - не должны быть единственным источником смысла страницы

## Что должно работать без JS

- чтение списка задач
- навигация по якорным ссылкам
- просмотр структуры страницы скринридером
- базовая видимость секций
- понимание приоритетов и статусов задач

## Что считается enhancement

- плавные переходы
- перехват навигации
- модальное создание задачи
- динамическое добавление карточек
- popover-меню действий
- клиентская фильтрация

## Правило гидратации

Чем меньше компоненту нужно «ожить», чтобы стать полезным, тем лучше он подходит для SSR.
```

#### `index.html` (принципиальные акценты)

Функционально страница остаётся той же, но мы рассматриваем её уже как **серверный HTML-контракт**.

Ключевые SSR-friendly свойства текущего `index.html`:

- полный документ с `header`, `nav`, `main`, `aside`, `footer`
- задачи уже присутствуют в HTML, а не рисуются только клиентом
- секции имеют понятные `id` и могут открываться по hash
- стили подключаются до скриптов
- скрипты идут с `defer` / `type="module"`
- native dialog/popover/details используются как enhancement-friendly примитивы

Фрагмент-напоминание в `<head>`:

```html
<!--
  SSR mindset:
  1. Этот HTML должен быть полезен сам по себе
  2. CSS tokens дают первый осмысленный экран
  3. JS только усиливает взаимодействие
-->
<link rel="preload" href="styles/main.css" as="style" fetchpriority="high">
<link rel="stylesheet" href="styles/main.css">
```

#### `components/README.md` (дополнение)

```markdown
## SSR notes

### `task-card`
- должен оставаться читаемым как обычная карточка контента
- slots передают смысл, доступный уже в server HTML
- JS-логика компонента не должна быть обязательной для понимания задачи

### `filter-panel`
- может использоваться как серверно отрендеренная оболочка
- содержимое формы фильтров приходит вместе с HTML
- раскрытие/взаимодействие усиливаются на клиенте
```

#### `scripts/main.js`, `styles/*`, `components/*.js`

Код поведения не ломаем.  
На этом этапе важнее архитектурная дисциплина, чем новые фичи:

- не переносить смысл интерфейса исключительно в клиентский рендер;
- не делать компоненты «пустыми оболочками», которые оживают только после JS;
- сохранять возможность позже подключить реальный SSR-движок (SSI, SSR framework, edge HTML) без переписывания всей системы.

### Как думать о FocusBoard в SSR-модели

```text
Server
  └─ отдаёт HTML + tokens/critical CSS
      ├─ пользователь уже видит задачи и структуру
      ├─ поисковик/скринридер уже понимают документ
      └─ браузер загружает JS
           └─ enhancement:
                navigation
                view transitions
                dialogs
                dynamic templates
```

Это и есть современный HTML-first подход 2026 года.

### Практический вывод

Если интерфейс невозможно понять или использовать без JavaScript, это не SSR-архитектура, а клиентское приложение с HTML-оболочкой.

FocusBoard сознательно строится иначе:

- HTML несёт смысл;
- CSS несёт представление;
- JS несёт поведение и удобство.

SSR возвращает HTML на центральное место архитектуры.  
Семантика, declarative components, design tokens и progressive enhancement — это не «учебные темы», а практический фундамент быстрых и устойчивых приложений.
