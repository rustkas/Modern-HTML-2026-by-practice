**Глава 21. Компонентное мышление и архитектура интерфейсов**

### Главная идея главы

Компонентное мышление — это способ проектировать интерфейс как систему независимых, предсказуемых блоков.  
В современном HTML это означает, что мы больше не думаем страницами из «дивов», а думаем контрактами:

- что является компонентом;
- где проходят границы ответственности;
- какой у компонента публичный API;
- что можно менять снаружи, а что является внутренней реализацией.

FocusBoard к этой главе уже содержит зачатки такой системы (`task-card`, `filter-panel`). Теперь мы фиксируем правила, по которым эта система будет развиваться.

### Принципы компонентного мышления в FocusBoard

1. **Одна ответственность**  
   Компонент делает одну понятную работу.

2. **Явный контракт**  
   Снаружи доступны только:
   - attributes/properties
   - slots
   - events
   - CSS-переменные / `part`

3. **Инкапсуляция**  
   Внутренняя разметка и стили не должны быть API по умолчанию.

4. **Композиция вместо наследования**  
   Сложные экраны собираются из простых блоков.

5. **Progressive Enhancement**  
   Базовая структура и смысл должны читаться даже до активации JS.

6. **Семантика прежде визуала**  
   Компонент сначала выражает смысл, потом оформление.

### Архитектурные роли в проекте

| Слой | Ответственность | Примеры |
|------|------------------|---------|
| Страница / маршрут | Сценарий пользователя | `index.html`, секции tasks/notes/settings |

# Компоненты FocusBoard

Это нативная UI-библиотека проекта, построенная на Web Components.

## Правила

1. Один компонент = одна ответственность
2. Публичный API должен быть явным
3. Shadow DOM используется для инкапсуляции реализации
4. Слоты описывают точки расширения
5. Темизация выполняется через CSS-переменные
6. Прикладная бизнес-логика не должна «протекать» внутрь UI-компонента без необходимости

## Компонент: `task-card`

### Назначение
Карточка задачи.

### Attributes
- `data-task-id` — идентификатор задачи
- `data-priority` — `high | medium | low`
- `data-status` — `active | completed`

### Slots
- `title` — заголовок задачи
- `media` — медиа-блок
- `description` — описание
- `priority-label` — текстовая метка приоритета/статуса
- `actions` — действия над задачей

### CSS-переменные
- `--task-border`
- `--task-radius`
- `--task-bg`
- `--task-padding`
- `--task-shadow`
- `--task-text`

### Пример
```html
<task-card data-task-id="10" data-priority="high" data-status="active">
  <h4 slot="title">Новая задача</h4>
  <p slot="description">Описание задачи</p>
  <span slot="priority-label">Приоритет: высокий</span>
</task-card>
```

## Компонент: `filter-panel`

### Назначение
Универсальная панель-оболочка для фильтров и похожих блоков.

### Slots
- `title` — заголовок панели
- default slot — содержимое панели

### CSS-переменные
- `--panel-border`
- `--panel-radius`
- `--panel-bg`

### Пример
```html
<filter-panel>
  <span slot="title">Фильтры задач</span>
  <form>...</form>
</filter-panel>
```
```

Содержимое рабочих файлов (`index.html`, `styles/main.css`, `scripts/main.js`, `components/task-card.js`, `components/filter-panel.js`) на этом этапе **не требует ломки API**.

Мы сознательно делаем акцент на архитектуре и соглашениях:

- код уже достаточно компонентный;
- теперь важно не столько добавить новых фич, сколько закрепить правила, по которым проект будет расти.

Это типичный зрелый шаг в реальной разработке: после появления компонентов сначала фиксируют систему, и только потом расширяют её.

### Как применять эти правила дальше

Когда появляется новый блок интерфейса, задаём вопросы:

1. Это отдельная ответственность или часть существующего компонента?
2. Какой у него публичный контракт?
3. Что должно быть снаружи через slots/attributes?
4. Что должно быть спрятано в Shadow DOM?
5. Нужен ли новый компонент или достаточно композиции существующих?

### Пример мышления

- Список задач — это сценарий страницы, не компонент.
- Карточка задачи — компонент.
- Меню действий — пока часть карточки/слота, не обязательно отдельный компонент.
- Панель фильтров — компонент-оболочка.
- Форма фильтров внутри панели — контент, который передаётся снаружи.

Именно так HTML-компоненты остаются простыми и не превращаются в «фреймворк ради фреймворка».

### Краткий итог главы

Компонентное мышление в современном HTML — это дисциплина границ.  
Мы проектируем не просто теги, а устойчивые блоки с понятным API, которые можно собирать в экраны.

FocusBoard теперь развивается не как монолитная страница, а как система:

- страницы описывают сценарии;
- компоненты дают переиспользуемые UI-примитивы;
- скрипты связывают поведение;
- токены задают общий визуальный язык.

В следующей главе перейдём к **HTML и Design Systems** и соберём эти правила в более цельную мини-дизайн-систему.
